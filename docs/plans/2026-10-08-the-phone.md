# The phone — JustWrite on Android and iOS (plan, 2026-10-08)

The program's step Q4, its last part (`2026-10-08-sync-and-quasar-program.md`). The scope is
decided — JustWrite's TASKS, "Sync — offline first…", decision 8: "the phone runs the book, its
images and versions, sync, and online AI providers". The engine side of the design is

## 1 · What it is

JustWrite's Capacitor build: the same app as the desktop, offline, on a phone or a tablet.

- **You write there:** your books — the manuscript and the story bible — with their images and
  saved versions.
- **It syncs** with your computers: through the cloud folder (signing in to OneDrive or Dropbox —
  needs the app registrations), by pairing with a computer (scan its QR code; the phone syncs with
  it over the Wi-Fi or Tailscale/ZeroTier), or with a file by hand (the share sheet and the file
  picker).
- **AI through online providers** (OpenAI, Anthropic, OpenRouter, Gemini, …) with your keys, the
  same features as the desktop.
- **Not on the phone:** the local AI engine (llama.cpp), the search index — so features that
  search the book by meaning (Chat about the book, character chat) are off there — the file
  autosave (the database is the save; the storage guard below protects it), backups and the book
  zip, Logs and Storage, listening for other devices (the phone connects to a computer; nothing
  connects to the phone).

## 2 · How it works

**The server runs inside the app, in a web worker** (the design's choice): JustWrite's own route
modules, unchanged where they're plain SQL — the book, versions, settings, sessions, the sweep
draft, the kit's provider, routing and preset routes — on:

- **SQLite WASM** over OPFS (`opfs-sahpool`, proven on the Android 16 emulator and the iOS 18.7
  simulator), behind a better-sqlite3-shaped facade so the kit's database wrapper
  (`platform/sql.js`) runs unchanged on it.
- **A small router** with the slice of Fastify the routes use (routes and `:params`, plugins,
  `onRequest`/`onResponse`/`preHandler` hooks, TypeBox validation, the kit's error handlers,
  `reply.code/type/header/send`, the AI stream's `reply.raw.write`). Sync's `onResponse → flush`
  is kept.
- **Import shims** in the worker bundle: `node:crypto`'s `randomUUID`/`randomBytes` from Web
  Crypto, `Buffer` from a small library, `undici` → the global `fetch`; the kit's barrels and
  top-level `process.platform` reads made worker-safe (§6).

**Requests reach it through one door.** The kit's ten `fetch` calls (`serverApi.js` ×4,
`client.js` ×4, `SyncPanel.vue` ×2) go through one transport an app can replace; on the phone it
hands the request to the worker and builds the `Response` from its answer, streams included.

**Images by id.** An `<img src>` can't reach a worker, and today a scene stores the server's
absolute address (`RichEditor.vue:1002` → `imageStore.js:71`: `http://127.0.0.1:17495/v1/images/…`),
which is also wrong on any other computer whose server sits elsewhere — found while mapping, no
stored scene has an image yet. Scenes store the image's id; the editor shows it through a URL made
at display time (the server's on a computer, a `blob:` from the worker on the phone); an absolute
address already stored is read back to its id.

**Sync on the phone:** the engine in the worker (`sqliteWasmAdapter`); a phone twin of the app
layer (the device id kept in the app's storage, no machine hash; no listening); the scene-text
adapter's HTML parsing on a pure-JS DOM in the worker (there is no `DOMParser` in a worker — the
server's `@tiptap/html/server` uses happy-dom, which needs Node). **The storage guard:** the phone
also writes its change files to its native data folder (`@capacitor/filesystem`) and rebuilds from
them if the webview's database is ever found empty. **Plain HTTP to private addresses:** Android's
network config allows cleartext to private ranges; iOS gets `NSAllowsLocalNetworking`.

**Online AI:** the kit's LLM routes for remote providers, in the worker, without the runner
(`installLlm` probes hardware and starts processes — the phone builds the subset: the tables, the
seed, the routers, the provider registry). A provider's API must accept a call from a webview
(CORS); not all do, so the calls go out through Capacitor's native HTTP on the main thread.

The design:

At phone width (Quasar's `xs`, under 600 px) JustWrite keeps its desktop screens and routes. Quasar's
mobile behaviour carries the shell, and every surface reflows to one column. The tablet keeps the
desktop layout.

- **The shell** (built with the CLI-layout move): the sidebar is the layout's drawer, opened by ☰,
  over the page with a backdrop, closing on navigation. **The title bar:** ☰ · Back · the book's
  title on one line · Undo · Redo · AI status · Search. Forward, the rail toggle and the theme and
  light/dark pickers stay on the computer (Settings → Appearance has both pickers).
- **Page headers:** the title on its own row; the page's actions on the row below, wrapping.
- **Lists and details:** the list is its own screen and a row opens the detail (the routes already
  work this way). A table keeps its first column in view and scrolls sideways for the rest; the
  pager is one line.
- **Forms and cards:** one column; a page's card loses its outer margin.
- **The editor:** full width; its toolbar wraps without covering the text below it.
- **Dialogs:** the window's width (Quasar's full-width dialog) — the plan's "sheets". **Panels**
  (help, AI tasks): full width over the page.
- **Tooltips** answer a mouse hover or keyboard focus, never a tap.
- **Not on the phone** (what its in-app server doesn't have, §1), declared once in the boot
  (`installLlmUi`'s capabilities `localEngine: false, embeddings: false`; JustWrite's
  `bookIndexOn`, `PHONE_HIDDEN_SECTIONS`):

    engine console; the first-run offer's local option; warm-on-boot;
  - the search index's features: Ask the book, Talk to a character, the index settings;
  - Settings → Backups, Storage, Server and Logs.
