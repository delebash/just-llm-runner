## ⛔ THE LOAD-BEARING DECISION — the per-model Tune SAVE (design §6.5)

**The tension:** the user wants an **Apply/Save** in the Tune modal that persists a model's tuned switches directly (skip the Lab). But the current design (§6.5) DELIBERATELY has **no per-model switch layer** — switches layer base→type→hardware (`switch_resolve.py:20-21`: *"There is no per-job/per-feature switch layer — engine config is owned by the taskKind → preset cascade"*). The user's own example (`n_cpu_moe=37`, `spec-draft-n-max=2`) is **model AND hardware specific**. So a "save this model's switches" is a **design-doc change** and cannot be made unilaterally (rule #6). **Options surfaced to the user (the user must pick):**
- **(A) A new per-model switch layer** — a `ModelSwitch(model_id, flag_name, flag_value)` table (mirrors `PresetSwitch`/`HardwareSwitch`), inserted into `resolve_model_switches` as base→type→**model**→hardware. Simplest match to *"I tuned this model, remember it."* Loses hardware-portability (a different GPU wants a different `n_cpu_moe`) — user can re-tune.
- **(B) A per-(model, hardware) layer** — key on `(model_id, hw_key)`. Most CORRECT for the `n_cpu_moe` case (model+GPU specific). More complex (composite key + a UI that is honest about "this box").
- **(C) Save onto the Task preset** — write the tuned switches to `EnginePresetSwitch` for the relevant Task preset (the existing "keep a config" home). But that is per-TASK, not per-model, and this is where `modelApply` also writes the preset's `.model`/`.providerId` → the ONE place the two axes could collide (see orthogonality below).
- **(D) Save to `HardwareSwitch`** — REJECTED: it is per-GPU-ALL-models, so a model-specific `n_cpu_moe` would wrongly apply to every model on that GPU.
- **(E) Status quo** — Send-to-Tasks-Lab → Save as a Task preset. The user explicitly wants to AVOID this detour.

**USER RECOMMENDATION (recorded, to open the discussion): keep the tune-save OFF the `modelApply` kit surface.** Rationale (agreed this session): tune-save is a **switch-layer concern**, `modelApply` is a **which-model concern** — they are orthogonal axes on different tables (`modelApply` → `engine_presets.model`/`.providerId` + `routing.embeddingModel`; switches → `switch_presets`/`hardware_switches`/`engine_preset_switches`). Keeping per-model-save on a switch layer (A or B) — NOT routed through `modelApply`/`engine_presets` — means the two never write the same rows and never conflict (the user's stated goal: *"i just dont want to have conflicting issues"*). Option (C) is the one that WOULD touch `engine_presets`, so it is the option the user's recommendation steers AWAY from. **This is the first thing to settle next session; NO code until the user picks A/B/(C) and confirms.**

### Orthogonality / conflict analysis (why 3b-ii-b and tune-save don't collide)

- Tune/switches read+write `switch_presets` + `hardware_switches` (+ `EnginePresetSwitch` via the Lab) — the FLAGS. `TuneMeasureModal` doesn't even import `modelApply` (it uses `labHandoff` + `/load` + `/measure`).

The ONLY collision risk is option (C) writing `engine_presets` — which the "keep it off modelApply" recommendation avoids.

## NOT a regression of the dropped `model_switches` (adjudicated — the panel should check this reasoning, not flag the name collision)

`seed.py:162-164` records that an earlier per-model switch table named `model_switches` was DROPPED: it held per-model COPIES of the dense/moe TYPE rules — seed-data duplication, the exact T3 failure ("the dense/moe TYPE rules live ONCE on the type presets"). The NEW table is a different thing wearing a similar name: it stores **per-(model, machine) MEASURED USER TUNES** — data that CANNOT live on a type preset (it differs per model×box) and is never seeded (user-written only, no `DEFAULT_*` seed, no `built_in` rows). The type rules continue to live once on the type presets; the new layer holds only what the user measured on a specific box. To avoid archaeology confusion the new table is named **`model_tunes`** (class `ModelTune`) — deliberately NOT reusing the dropped `model_switches` name.

## Grounded wiring facts (verified this session, 2026-07-05 — the plan builds on these exact seams)

- **`hw_key` is NEVER passed in production today.** `install.py:162-169` wires `switches_fn(model_id)` → `resolve_model_switches(model_id)` with the default `hw_key=""`; `lifecycle.py:728` calls `self._switches_fn(model_id)`; `lifecycle.py:850` same. So the `HardwareSwitch` layer (`switch_resolve.py:60-62`) is DORMANT in the live path — `hardware_switches` rows are unreachable at load. Plan B wires a machine key through this seam (fixing the dormant layer as a side effect).
- **Machine facts for the key all exist in `hardware.detect()`** (`hardware.py:145-167`): `HardwareInfo(os, platform, cpu_cores, ram_mb, gpus=[GpuInfo(vendor, name, vram_mb, driver, compute_cap)], runtimes)`. `max_vram_mb()` (`hardware.py:26-30`) is the single VRAM reduction.

## THE DESIGN (what gets built)

### D1 — the `model_tunes` table (the B layer)
```
class ModelTune(LlmBase):                     # llm/db.py, next to HardwareSwitch (:226)
    __tablename__ = "model_tunes"
    model_id  = Column(String, primary_key=True)   # soft ref to model_catalog (no FK — matches ModelSampler/HardwareSwitch)
    hw_key    = Column(String, primary_key=True)   # the MACHINE key (below)
    flag_name = Column(String, primary_key=True)   # an Overrides field name (same vocabulary as preset_switches)
    flag_value= Column(Text,   nullable=False, default="")
```
No `built_in` column — this table is NEVER seeded; user-written only (that is the distinction from the dropped `model_switches`). Variable rows (flag per row) — a new switch needs no schema change (the `PresetSwitch`/`HardwareSwitch`/`EnginePresetSwitch` pattern).

### D2 — the machine key (`hw_key` becomes whole-machine, single source)
New `machine_key(hw: HardwareInfo) -> str` in `runner/hardware.py` (beside `max_vram_mb`, the same "one reduction, one source" principle): `"{gpu.name}|{gpu.vram_mb}|{cpu_cores}c|{ram_gb}g"` from the FIRST/max GPU, or `"cpu|{cpu_cores}c|{ram_gb}g"` with no GPU; `ram_gb = ram_mb // 1024` (whole GB — absorbs MB-level reporting jitter). Plus a memoized `current_machine_key()` (functools `@cache` over `machine_key(detect())`) so the llm-side wiring never re-runs `nvidia-smi` per call. WHY whole-machine, not GPU-only (the Google-corroborated point): `threads` is CPU-core-driven and `batch`/`ubatch` are RAM/bandwidth-driven, so two boxes sharing a GPU model but differing in CPU/RAM must not collide. `hardware_switches` adopts the SAME key (it is fed by the same wire) — its docstring `db.py:227-229` updates from "keyed by GPU" to "keyed by machine". Pre-production: no migration of old `hw_key` rows (drop+reseed is free; the layer was dormant anyway — nothing real to migrate).

### D3 — resolver layering (last wins): `base → type(moe|dense) → mtp(auto, gated) → hardware → model-tune`
`resolve_model_switches(model_id, hw_key="")` (`switch_resolve.py:36`) gains two layers:
- **`mtp` (the auto-enable reversal):** re-seed the `mtp` SwitchPreset (`applies_to="mtp"`) and apply it when the GATE passes: **`model.mtp OR mtp_draft_file != ""`**. **⛔ PANEL FIX (architecture checker, T1):** the earlier draft's gate `model.mtp AND (built-in OR draft-configured)` could NEVER fire for the flagship Gemma case — `mtp` is header-derived from the MAIN file (`identity.py:63` sets `mtp = meta.is_mtp` from `nextn_predict_layers`), which is exactly what a draft-style model LACKS, so the `model.mtp AND …` form blocked the draft arm structurally (and, as the grounding checker noted, its truth table reduced to plain `model.mtp` — the disjunct was dead). The corrected two arms are INDEPENDENT: built-in = header-derived `mtp` true (Qwen-style, `nextn_predict_layers` in the main GGUF); draft-style = `mtp_draft_file` configured (Gemma-style) — regardless of the `mtp` bool, which stays header/user-driven. This also makes the D8 Edit-form copy literally true: *setting the MTP draft file IS what enables auto-MTP for a draft-style model.* A hand-checked MTP on a model that is neither built-in-capable nor draft-configured is the same user error as hand-setting the `spec_type` knob today — it fails at load with llama-server's own error; documented, not specially handled. Seed content: `{"spec_type": "draft-mtp"}` — and `spec_n_max` ONLY if the user's OPEN-KNOB-#1 pick differs from the knob-catalog default (`2` → seed it, a distinct measured value; `3` → seed NOTHING for `spec_n_max`, because the knob default already says 3 and seeding a copy is the exact one-source violation Phase 3 removed — the reuse checker's guardrail). Being a normal `switch_presets` row it is USER-EDITABLE like everything else (the "everything the app ships must be user-editable" standing principle) — and because it sits BELOW hardware + model-tune, unchecking MTP in Quick tune saves `spec_type=none` into the model-tune layer, which wins. The Phase-3 "never auto-enable" docstrings (`switch_resolve.py:12-18`, `seed.py:162-183`, `switch_presets_api.py:8-10`, `db.py:164-165`) all rewrite to the new gated-auto-enable truth, citing this decision.
- **`model-tune` (the B layer, LAST so it always wins):** `if hw_key: merged.update(rows of ModelTune where model_id AND hw_key)`. Model-tune ABOVE hardware because a value you measured for THIS model must beat a blanket per-machine value (the user tuned it deliberately).

### D5 — save semantics: VERBATIM SNAPSHOT (adjudicated)
Quick tune **Save** writes ALL non-empty grid rows as the `(model, machine)` tune, verbatim (PUT replaces the whole set — the `switch_presets_api.py:6` "the PUT replaces a preset's WHOLE flag set" precedent). REJECTED alternative — diff-vs-lower-layers: (a) the user's mental model is "save THIS config" (their gemma `.ini` IS a full verbatim config); (b) diff semantics silently mutate a saved tune when a lower layer's seed later changes — a measured config must stay exactly what was measured; (c) diffing breaks the uncheck-MTP case only verbatim handles trivially (`spec_type=none` saved explicitly). The cost — base-preset improvements don't auto-flow into an already-saved tune — is the POINT of a measured snapshot; "Remove saved tune" (DELETE) returns the model to the layered defaults.

**Stale/unknown-row degradation (panel fold — arch checker T5c):** a saved tune row whose `flag_name` is not a typed `Overrides` field flows to `extra_flags` VERBATIM (`_switches_to_overrides`, `lifecycle.py:219-242`; `_OVERRIDE_FIELDS` derives the known set from the dataclass at `lifecycle.py:180`). That passthrough is a FEATURE for deliberate raw flags (custom KnobGrid rows work today because of it) — but it means a typed field the runner later DROPS (say a future version removes `reasoning_budget`) would suddenly render with its underscore spelling (`--reasoning_budget`) and hard-fail llama-server, with only "Remove saved tune" as recovery. Adjudicated middle course (preserves the raw-flag feature, kills the silent failure): the RESOLVER does NOT prune — but the Tune modal BADGES any saved row it cannot match against the knob catalog / Overrides field set as *"unrecognized — remove or fix"* (built in T4, tested with a bogus saved flag), so a stale row is visible BEFORE it fails a load. Recorded honestly: a runner flag-drop can invalidate saved tunes; the badge turns that from a mystery load failure into a labeled row.
